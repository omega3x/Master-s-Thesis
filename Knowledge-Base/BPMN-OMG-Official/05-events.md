# События в BPMN (OMG)

Источник: OMG BPMN 2.0, глава 10, подраздел Events.

---

## Что такое Event

**Event** — нечто, что **происходит** в процессе. Влияет на поток выполнения.

Графически: **круг**. Различаются по:

- положению (start / intermediate / end);
- типу триггера (timer, message, error, signal и др.);
- поведению (catch vs throw).

---

## Три положения событий

| Положение | Роль | Маркер |
|-----------|------|--------|
| **Start Event** | Начало процесса или подпроцесса | Тонкая граница |
| **Intermediate Event** | Между start и end | Двойная граница |
| **End Event** | Завершение пути в процессе | Толстая граница |

Start Event **создаёт token**. End Event **уничтожает token**.

---

## Catch vs Throw

| Тип | Значение |
|-----|----------|
| **Catch (ловящее)** | Процесс **ждёт** наступления события |
| **Throw (генерирующее)** | Процесс **инициирует** событие |

Пример: Message Catch — ждём сообщение; Message Throw — отправляем сообщение.

---

## Основные типы триггеров

| Триггер | Применение |
|---------|------------|
| **None** | Простой старт/конец без специфики |
| **Timer** | Срок, период, SLA, эскалация |
| **Message** | Асинхронный обмен между участниками |
| **Signal** | Широковещательное уведомление |
| **Error** | Обработка ошибки |
| **Escalation** | Эскалация наверх |
| **Conditional** | Условие на основе выражения |
| **Terminate** | Немедленное завершение всего процесса |

---

## Boundary Events (граничные события)

**Boundary Event** прикрепляется к **Activity** (обычно task или subprocess).

| Свойство | Значение |
|----------|----------|
| `attachedToRef` | К какой задаче прикреплено |
| `cancelActivity` | Прерывает ли задачу (true) или параллельно (false) |

**Пример в проекте:** `Boundary_TimerEscalation` на задаче подписи в `test3.bpmn` — 5-day SLA, при срабатывании эскалация декану (`cancelActivity="false"`).

---

## Event Subprocess

**Event Subprocess** — подпроцесс, запускаемый **событием** (часто error или escalation), а не sequence flow.

Используется для **обработки исключений** без загромождения основного потока.

---

## Несколько End Events

Процесс может иметь **несколько** end events:

- успешное завершение;
- отказ;
- отмена.

**Пример:** `test3.bpmn` — `End_Rejected` и `End_DiplomaIssued`.

---

## Timer Events на практике

Timer может задавать:

- duration (PT5D — 5 дней);
- date;
- cycle (повтор).

Для **оптимизации** timer events добавляют:

- контроль SLA;
- эскалацию при задержке;
- периодический polling (batch jobs).

Camunda пример Two Step Escalation (`BPMN/01-bpmn-examples/08-two-step-escalation.md`) показывает три способа моделирования таймеров.

---

## Рекомендации для моделирования

1. Start Event **всегда** должен иметь label (что запускает процесс).
2. End Event описывает **результат** («Application rejected», «Diploma issued»).
3. Intermediate events не злоупотреблять — каждое должно иметь бизнес-смысл.
4. Boundary timer — стандартный паттерн для **оптимизации времени** ожидания.

---

## Связь с AI-генерацией

System Prompt требует: start/end events, timer events, intermediate events «when appropriate». OMG семантика: каждое событие должно иметь корректные incoming/outgoing flows и определение триггера в XML.
