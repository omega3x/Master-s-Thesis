# Техники prompt engineering из статьи

Статья сравнивает **три подхода** к взаимодействию с GPT-3.5 для улучшения semantic quality BPM.

---

## 1. Zero-shot prompting

**Определение:** промпт **без примеров** — только инструкция и контекст модели.

**Когда использовать:** быстрый первый проход, когда нужен широкий список идей.

**Типичная структура:**

1. Роль: «ты эксперт по предметной области X»
2. Ограничение: «не рисуй диаграмму»
3. Вход: список текущих lanes, activities, artifacts
4. Задача: «предложи недостающие activities и artifacts»
5. Формат ответа: нумерованный список с обоснованием

**Сильные стороны:** простота, мало токенов.  
**Слабые стороны:** менее предсказуемый формат, может быть слишком общим.

---

## 2. Few-shot prompting

**Определение:** промпт **с 1–2 примерами** хороших предложений до основного запроса.

**Когда использовать:** когда нужен стабильный формат ответа и более точные domain-specific предложения.

**Типичная структура:**

1. Роль
2. **Пример 1:** «для процесса госпитализации не хватает: Verify insurance (Secretary)»
3. **Пример 2:** «не хватает артефакта: Insurance card copy»
4. Вход: наша текущая модель
5. Задача: «предложи в том же формате»

**Сильные стороны:** LLM копирует структуру примеров, выше точность.  
**Слабые стороны:** длиннее промпт, примеры могут смещать ответ в сторону домена примеров.

---

## 3. Chain-of-Thought (CoT) prompting

**Определение:** промпт требует **пошагового рассуждения** перед финальным списком предложений.

**Когда использовать:** сложные процессы с несколькими ролями и неочевидными зависимостями.

**Типичные шаги в CoT (по логике статьи):**

1. Определи предметную область процесса
2. Перечисли стандартные роли для этой области
3. Для каждой роли — типичный набор activities
4. Сравни с текущей моделью — что отсутствует?
5. Для каждой activity — какие artifacts нужны?
6. Ранжируй предложения по важности
7. Выведи финальный список

**Сильные стороны:** лучше для сложных моделей, прозрачное обоснование.  
**Слабые стороны:** дольше, больше токенов, нужна проверка рассуждений.

---

## Что передавать в промпт (input configurations)

По статье, качество зависит от **того, какие элементы модели включены в промпт**:

| Конфигурация | Содержание промпта |
|--------------|-------------------|
| Только activities | Список задач без контекста ролей |
| Activities + lanes | Задачи с привязкой к ролям |
| + artifacts | Плюс документы и данные |
| + relationships | Плюс связи lane–activity–artifact |

**Вывод для нашего проекта:** чем полнее контекст (lanes + activities + data objects), тем полезнее предложения LLM.

---

## Чего НЕ делать (по духу статьи)

- Не просить «нарисуй BPMN XML» в том же запросе, где ищете недостающие концепции.
- Не принимать все предложения LLM без проверки экспертом.
- Не смешивать semantic enhancement с layout/координатами диаграммы.

Генерация XML — отдельная задача (у нас: `System Prompt/SystemPrompt.md` + конвертер XPDL).
